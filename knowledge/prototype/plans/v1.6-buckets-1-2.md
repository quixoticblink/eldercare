# Kakis v1.6 — Buckets 1 and 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the 18 features in Buckets 1 and 2 of `feature-buckets-2026-09-04.md` as v1.6 of the Kakis app, each behind a Playwright end-to-end assertion and a smoke-test assertion, one commit per feature, then deploy to the live box.

**Architecture:** FastAPI + DuckDB backend (`app/backend`), no-framework JS frontend (`app/frontend`). Every task names its owning module from `app/SPEC.md` §2 and touches only that module's files plus `db.py` for migrations. Schema changes are `ADD COLUMN IF NOT EXISTS` followed by `CHECKPOINT`. New end-to-end suite in `app/tests/e2e/` (`@playwright/test`) runs against a throwaway DuckDB on port 8100.

**Tech Stack:** Python 3.13, FastAPI 0.141, DuckDB 1.5.5, uvicorn, `@playwright/test` (Chromium), existing `backend/tests/smoke.py` (FastAPI TestClient).

**Spec:** `knowledge/prototype/feature-buckets-2026-09-04.md` (the what and the order), `app/SPEC.md` (the module contract), `knowledge/prototype/tabletop-2026-08-21-feedback.md` and `ncss-app-review-2026-08-18.md` (the why).

## Global Constraints

- Module boundaries per `app/SPEC.md` §2. Routers never import each other. Frontend views call the network only through `api.js`.
- Hard rules (SPEC §9.5): no public ratings; the kaki never sees the caregiver's start code (`otp_code`); urgent sorts first; every money figure carries `UI.moneyNote()`.
- Migrations: `ALTER TABLE … ADD COLUMN IF NOT EXISTS` in `db._init`, before the existing `CHECKPOINT`. New tables via `CREATE TABLE IF NOT EXISTS`.
- Decisions already taken: flexible duration is charged at the same hourly rate, **prorated to the half hour, minimum 1 hour**; identity runs both ways — the kaki shows a **photo and a 4-digit kaki code**; the caregiver enters the kaki code, which **reveals** the caregiver's start code; the kaki then enters the start code to begin.
- Decisions taken in this plan (the bucket file left them open): photos and certificates are stored **base64 in DuckDB** (`TEXT` columns), capped client-side (photo ≤ 200 KB after canvas resize to 320 px; certificate ≤ 1 MB, PDF/JPEG/PNG). One file, covered by the existing backup, no new Python dependency. Kaki availability moves from half-day grid to **per-day from/to in 30-minute steps**; legacy half-day slots convert on read (morning → 08:00–13:00, afternoon → 13:00–18:00). Visits gain `start_time`, `end_time`, `hours`; the existing `time_window` column is kept and written as `"HH:MM–HH:MM"` so `availability.half_day_for_window` and every display keep working.
- Every user-visible change updates SPEC §9. Every task adds a line under a new `v1.6` heading in SPEC §10 (written once at the end, in the record task, but each commit message names the feature and module).
- Assertions: each task adds ≥1 Playwright assertion in `app/tests/e2e/` and ≥1 `assert` in `backend/tests/smoke.py`.
- Test loop per task: write failing Playwright test → run, see it fail for the right reason → implement → run the single spec green → run `smoke.py` and the full e2e suite green → for schema tasks, restart the server and rerun `lifecycle.spec.js` → commit.
