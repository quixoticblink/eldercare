## What we learned

A hard rule that is enforced in one code path is a coincidence. "The kaki never sees the
start code" was true of the visit page and false of the list, the accept, the start and
the complete responses, since v1. Nobody looked because the screen never showed it.

The clock is infrastructure. Every "has this window passed" and "how far ahead" rule was
a Singapore rule computed on a UTC box, and the test suite pinned the clock so it
couldn't tell. The frontend agreed for the wrong reason (`toISOString`).

The reviews earned their place. Both were dispatched with the SPEC in hand and told to
be skeptical; between them: the code leak, the timezone, a regex that missed "9am–12", a
phone-only account able to lock itself out, a blank kaki code verifying visits assigned
before the upgrade, and HTML from a cancellation reason reaching an email.

Tests that share names collide. Every seed reused "Tan Bee Lian"; the roster test had to
pick rows by id. Small, but the kind of thing that costs an hour at 2am.

## What changed

- The door runs both ways: kaki photo and code, then the family's start code.
- Exact times, half-hour billing, one-hour minimum. Kaki hours per day.
- Preferences: female or male kaki; the same kaki again. Both sort, never filter;
  auto-match honours both.
- Cancellation is a lifecycle with reasons, on both sides, visible to the coordinator.
- Certificates are in the app and on the approval card, including for pending kakis.
- The wall before the product is lower: no placeholder number, a waiting screen that
  says what to do, required fields marked, refresh keeps your step, no window offered
  after it has passed.
- 156 → 368 smoke assertions; 24 end-to-end specs; `TZ` pinned; `App.config` fixed
  (PayNow and the money disclaimer had never reached the UI).
